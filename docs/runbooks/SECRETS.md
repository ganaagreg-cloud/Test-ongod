# Secrets and environment variables

One row per variable in `.env.example`. **Names and explanations only: no values in this vault, in git or in chat.** Related: [[DEPLOY]], [[BUNNY_SWITCH]], [[ADR-0016-monitoring-logs-alert-emails|ADR-0016]], [[ADR-0018-auth-implementation-details|ADR-0018]], [[ADR-0022-admin-totp-session-proof|ADR-0022]], [[ADR-0023-subscription-workflows-implementation|ADR-0023]].

## Rules

1. **Fresh secrets per environment.** Local, staging and production never share a value. A value that was ever used in dev (or pasted anywhere) is not used in production.
2. **We generate our own secrets, straight into the target.** Command, run on the machine that needs it, output written directly into `.env` or the hosting panel, never copied through a chat or a file that is shared:
   `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`
3. **No secrets in chat.** Not in WhatsApp, Slack, email, tickets, screenshots, pull requests, AI assistants or this vault. If a secret appears anywhere it should not, treat it as leaked and rotate it (see "Leak response").
4. **`.env` is git-ignored; `.env.example` has placeholders only.** Production values live in the hosting panel and in the shared vault, nowhere else.
5. **Shared vault for handover.** All production secrets and account logins are stored in one shared password-manager vault (for example Bitwarden or 1Password) that both Ganaa and the owner can open. Nothing important exists only on one person's laptop.
6. **Handover = rotate.** When the project moves to the owner: the owner creates their own accounts (Bunny, Apple, Google, Expo, hosting, mail), every secret is regenerated, and the old values are revoked, so copies that stayed with the developer stop working.
7. **Least access.** Give out the one value a person needs, not the whole `.env`. Remove access when someone leaves.

"Prod owner" below is **Ganaa until handover, then the owner**, for every row.

## Not in `.env`, but part of the handover

These accounts and files hold power over the product. Each is created in the **owner's** name (or transferred), stored in the shared vault, and the developer's access is removed at handover ([[STORE]], [[open-questions]] #1).

- **Apple Developer account** and its signing material (the `.p8` key, certificates). If lost, the iOS app cannot be updated.
- **Google Play Console account** and the Android **upload/signing keystore** (`.jks`). If lost or leaked, the Android app cannot be updated safely. Never commit it.
- **Expo / EAS account**: builds, and the push credentials uploaded there (Apple APNs key, Google FCM credentials). No Firebase value is in `.env`.
- **Google Cloud project** (OAuth clients for sign-in), **Bunny account**, **hosting panel**, **domain registrar**, **mail provider**, **Sentry**, **GitHub**.
- **Per-admin TOTP seeds** are stored in the database (`User.totpSecret`), not in env: a database leak exposes them ([[ADR-0022-admin-totp-session-proof|ADR-0022]]). A lost authenticator is reset by hand in the database.

## Rotation checklist

1. Generate the new value (rule 2) or create it at the provider.
2. Update the hosting panel env and the shared vault in the same step.
3. Restart the process; check `/health` and the one feature that uses the secret (login, an email, a playback link).
4. Revoke the old value at the provider.
5. Note the date and reason in the day's log (no values).

## Leak response

1. Rotate the leaked value now (checklist above); do not wait to be sure.
2. If it was `DATABASE_URL`, `BUNNY_STORAGE_API_KEY` or `BUNNY_CDN_TOKEN_KEY`: also check for unexpected data or file changes and the access logs.
3. If it was `JWT_ACCESS_SECRET` or a password hash source: force logins by revoking sessions in the database (`Session.revokedAt`) after rotating.
4. Write what happened in the log, without the value.
