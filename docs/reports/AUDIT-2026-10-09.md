## A. Access and money

Checked and OK: approve, reject, revoke and grant each take the user lock, use a conditional `updateMany` with a `count !== 1` check, and write Payment, `accessUntil`, AuditLog and the email/push jobs in one transaction (`admin/decisions.ts:58-102`). Double approval, parallel approval and approve-versus-reject races are tested and pass. Only PAYMENT_SUBMITTED can be approved or rejected; only ACTIVE can be revoked (`decisions.ts:64,113,148`). The period starts at max(now, latest ACTIVE end) (`subscriptions/period.ts:19-23`). `accessUntil` is written only by `decisions.ts:20-32` (and the seed). Play is refused on the server when `accessUntil <= now`; the URL lifetime is min(now + 4 h, accessUntil) (`catalog/service.ts:263-283`). DISABLED, DELETED and PENDING_PROFILE users are stopped by the guard (`auth/guard.ts:47-52`). Reference codes use `crypto.randomInt` over 31 unambiguous characters, with a unique index and 5 retries (`period.ts:5-13`, `service.ts:98-101`), and are never used for authorization. The reminder is sent once (`reminderSentAt IS NULL` precondition in the same transaction, `cron/tasks.ts:81-97`). There is no update or delete path for AuditLog or Payment in app code. `dev-approve` refuses production (`scripts/dev-approve.ts:9`).

#### A-01 · P1 · No production bootstrap for the Plan, OWNER, demo account and min versions; the dev seed is unguarded

- **What:** No route or script creates a `Plan`, the OWNER, the store demo account or the `min_version_*` AppConfig rows; only `prisma/seed.ts` does. The seed has no `NODE_ENV` check. It writes `accessUntil` directly, without approval or an audit entry (dev user `bat` +300 days, `demo` +365 days), and gives all seeded users the same `SEED_USER_PASSWORD`. Two docs point production at it: [[STORE]] ("seed user `demo`") and [[ADR-0022-admin-totp-session-proof|ADR-0022]] ("owner account is created by the developer (seed)"). [[SECRETS]] says the seed must never run against production.
- **Evidence:** `apps/api/prisma/seed.ts:9-16` (env parse only, no production guard), `:42-46` (plan upsert), `:73`, `:86`, `:160`. Compare `scripts/dev-setup.ts:6` and `dev-approve.ts:9`, which do have the guard. No `plan.create|upsert` in `apps/api/src`.
- **Reproduce:** Deploy to a fresh database: `GET /v1/plans` is empty, so nobody can subscribe. Or follow STORE.md and run the seed in production: fake users get free access with a shared password and no audit row.
- **Fix:** Add a guarded `ops:bootstrap` script (OWNER from a prompt, Plan and AppConfig from arguments, refuses to overwrite). Make `seed.ts` refuse `NODE_ENV=production`. Create the demo account via register + admin grant, and write that path into DEPLOY.md and STORE.md.
- **Scope:** IN · **Confidence:** VERIFIED (code). Whether anyone plans to run the seed in production is UNVERIFIED.

#### A-02 · P2 · A user who paid but missed the 7-day window, or never pressed "Төлсөн", cannot be approved; the money is recorded as 0 ₮

- **What:** Approve accepts only PAYMENT_SUBMITTED. A PENDING_PAYMENT older than 7 days cannot be submitted any more. The only way out is a manual grant, which writes `amountMnt: 0` and a `MANUAL_GRANT` payment and sends no email or push. The money the bank received is then missing from Payment, the CSV export and the audit log. Separately, `current()` still returns bank details for a stale PENDING_PAYMENT until the cron runs, so day 8 can still show them.
- **Evidence:** `admin/decisions.ts:64` (`sub.status !== 'PAYMENT_SUBMITTED'`), `:195,204` (`amountMnt: 0`); `subscriptions/service.ts:123,138`.
- **Reproduce:** Create a request, transfer the money, don't press "Төлсөн", wait 8 days → the admin has only "grant", recorded at 0 ₮.
- **Fix:** Let the admin approve a PENDING_PAYMENT or stale-EXPIRED request with a status precondition and the amount received (BANK_TRANSFER), or let grant record an amount and method.
- **Scope:** IN (edge case of SPEC E) · **Confidence:** VERIFIED

#### A-03 · P2 · Scheduled tasks run only when an outside cron calls `/v1/cron/tick`, and nothing alerts when it stops

- **What:** Reminders (SPEC F), the 7-day expiry, ending periods, scheduled publishing and upload clean-up run only from `POST /v1/cron/tick`. The in-process loop drains jobs but never runs these tasks. With no host cron, scheduled episodes never go live and reminders stop silently. With a 5-minute cron ([[DEPLOY]] step 6), publishing can be up to 5 minutes late.
- **Evidence:** `server.ts:26,77` (only `worker.start()`); `routes/cron.ts:31-49`; `cron/tasks.ts:159-165`; `app.ts:171-179`.
- **Reproduce:** Run without the host cron and schedule an episode → it stays SCHEDULED.
- **Fix:** Also run the (idempotent) cron tasks from the in-process loop every 1–5 minutes. Alert when the last tick is more than 15 minutes old.
- **Scope:** IN · **Confidence:** code VERIFIED. iTools cron availability UNVERIFIED.

#### A-04 · P2 · The approval log loses the approver's name when an admin deletes their own account

- **What:** AuditLog stores only `actorId`; the name shown comes from the live User row. `DELETE /v1/me` works for any role and renames the user to `deleted-<id>`, so every approval that admin made now shows "deleted-…", and the name cannot be recovered. Nothing stops the only OWNER from deleting themselves.
- **Evidence:** `admin/queries.ts:44` (`actor: { id, username }` read live); `auth/service.ts:542-558` (no role check).
- **Reproduce:** An admin approves a payment, then calls `DELETE /v1/me` → the audit page shows actor "deleted-…".
- **Fix:** Copy the actor's username and role into `AuditLog.data` at write time. Refuse self-deletion for ADMIN/OWNER (or require another OWNER).
- **Scope:** IN · **Confidence:** VERIFIED

#### A-05 · P2 · The 14-day reminder can be starved by periods that are skipped but never marked

- **What:** A period skipped because it was renewed early (or the user is deleted or disabled) keeps `reminderSentAt = null`. It is picked again on every tick (`orderBy endsAt asc`, `take 200`). With more than 200 such rows inside the 14-day window, reminders that are actually due never go out. This is plausible one year after launch, when the launch-week cohort renews at the same time.
- **Evidence:** `cron/tasks.ts:58-67` (select), `:74-79` (`return false` without marking).
- **Reproduce:** 201 ACTIVE periods ending within 14 days, each with a later stacked period, plus one ordinary period → the ordinary one never gets a reminder.
- **Fix:** Exclude renewed periods in the `where`, or stamp `reminderSentAt` when skipping; page with a cursor.
- **Scope:** IN (SPEC F) · **Confidence:** VERIFIED by reading; no test covers it.

#### A-06 · P3 · "1 year" means 365 × 24 h ending at the approval time of day, but users see only a date

- **What:** `endsAt = startsAt + days × 24 h`. A period across 29 February ends one calendar day early (approved 2027-03-01 10:00 UB → ends 2028-02-29 10:00 UB). Access ends at the approval time of day, while the portal and email say "YYYY.MM.DD хүртэл". 23:59 versus 00:00 UB is handled consistently: every surface formats in Asia/Ulaanbaatar.
- **Evidence:** `subscriptions/period.ts:22`; `lib/dates.ts:7`; portal `i18n/mn.ts:200,216`. Pure script `scratchpad/A/period-check.ts`.
- **Reproduce:** Approve at 10:00 UB → the portal shows next year's date, but access ends at 10:00 on that date.
- **Fix:** Decide: round `endsAt` to 23:59:59 UB of the last day, or add calendar years.
- **Scope:** IN (matches SPEC "plan's days") · **Confidence:** VERIFIED

#### A-07 · P3 · The portal Status page tells an active member their request ended

- **What:** `current()` returns the newest subscription by `createdAt`. An active member who starts a renewal and lets it expire unpaid sees "Энэ хүсэлтийн хугацаа дууссан" and "choose a plan". The Account page is correct.
- **Evidence:** `subscriptions/service.ts:115-118`; `apps/portal/src/pages/Status.tsx:125-133`.
- **Reproduce:** An ACTIVE member creates a renewal request and lets it pass 7 days → open /status.
- **Fix:** When `accessUntil > now`, show the ACTIVE period instead.
- **Scope:** IN · **Confidence:** VERIFIED

#### A-08 · P3 · Account deletion leaves the user's request in the admin queue; rejecting it emails a dead address

- **What:** `deleteAccount` does not cancel open requests. Reject has no DELETED check and queues an email to `deleted-<id>@deleted.invalid`, which retries and then sends a failed-job alert to the owner.
- **Evidence:** `auth/service.ts:545-564`; `admin/decisions.ts:110-131`.
- **Reproduce:** Submit a payment, delete the account, reject the request in admin.
- **Fix:** In the deletion transaction, set open requests to CANCELLED. Skip mail for DELETED users.
- **Scope:** IN · **Confidence:** VERIFIED

## B. Media, playback and push

Checked and OK:

- **Signing:** done only on the server; the key comes only from env (`env.ts:85`, `app.ts:72-75`). No Bunny key, host or HMAC appears in mobile, admin or portal.
- **Token oracle:** a pure script with a dummy key (`scratchpad/B/oracle.ts`) gives byte-identical URLs to Bunny's reference `token.js`, and the token changes when the path or expiry changes. Covers use their own per-file tokens with no `token_path`, so a cover token cannot unlock audio (`catalog/media.ts:30-40`).
- **Play order:** access, then registered device, then published, then READY; `Cache-Control: no-store` (`routes/catalog.ts:52`).
- **Device limit:** holds on login, refresh, social login and in a login race (`auth/service.ts:198-224,385-403`; `auth.test.ts:284,361,370,460`). Logout frees the slot. A second phone that logs in with the same deviceId revokes the first phone's sessions (`service.ts:250-251`), so one id cannot be shared at the same time.
- **tus uploads:** every method (POST/HEAD/PATCH/DELETE) is behind `requireAdminTotp`, and the uploader header is overwritten after the guard (`routes/admin-content.ts:59,184-197`). Max 512 MB; the Bunny upload runs in a job.
- **Failed media:** shows the reason plus Retry (`AudioUploader.tsx:215,279-289`).
- **Scheduled publish:** happens once and never early (`cron/tasks.ts:117-135`, catalog requires `publishedAt <= now`).
- **Paths:** storage paths are built from IDs only.

#### B-01 · P1 · No push token is ever stored, so every push goes to nobody

- **What:** No API route writes `Device.pushToken`; it is only read and cleared by the push job. The mobile app has no `expo-notifications`. The push job finds no tokens and returns silently. This affects the approval push, the access-ending push and the (missing) new-episode push.
- **Evidence:** `pushToken` appears only in `apps/api/src/push/index.ts:82-92` and in `test/push.test.ts`, which writes it directly into the DB. No `expo-notifications` in `apps/mobile/package.json`, and none in the `expo config` plugins (`expo-router, expo-secure-store, expo-image, expo-audio`).
- **Reproduce:** Log in from any client, then check the Device row: `pushToken` is always NULL. Approve a payment: the `push.send` job sends nothing.
- **Fix:** Add a zod-validated `PUT /v1/me/push-token` that sets the token on the session's Device, with access-rule tests. Mobile: the `expo-notifications` plugin, a permission prompt and a token upload after login (phase 3).
- **Scope:** IN (SPEC F, G). API part MISSING; mobile part NOT STARTED. · **Confidence:** VERIFIED

#### B-02 · P1 · Publishing an episode sends no "new episode" push

- **What:** SPEC G: "Push to all active users on publish". Neither "publish now" nor the scheduled publish queues a push or a Notification row. `enqueuePush` has exactly two callers: the payment approval and the access-ending reminder.
- **Evidence:** `apps/api/src/admin/content.ts:247-263` (`publish`: `updateMany` + audit only); `cron/tasks.ts:114-138` (`publishScheduledEpisodes`, no push); `enqueuePush` callers are only `admin/decisions.ts:96` and `cron/tasks.ts:92`.
- **Reproduce:** Publish or schedule an episode → the Job table has no `push.send` row.
- **Fix:** In the same transaction as the status flip (status precondition), queue one fan-out job keyed by episodeId. The job pages through users with `accessUntil > now` and queues their pushes. Add a test that it runs once.
- **Scope:** IN · **Confidence:** VERIFIED (no test covers it)

#### B-03 · P1 · Episode pictures are cropped to 1400×1400 squares, but the accepted design is 16:9

- **What:** [[ADR-0028-cream-library-and-16x9-artwork|ADR-0028]] (accepted) and [[DESIGN]] "Artwork" make episode pictures 16:9 (1280×720 recommended), with 16:9 player and hero and 4:3 list crops. The server still follows [[ADR-0021-catalog-and-playback-rules|ADR-0021]] #5 and centre-crops every upload to a 1400 and a 400 **square**. A YouTube-style 16:9 thumbnail loses about 44% of its width. The mobile kit then crops that square again into 16:9 or 4:3. The admin hint tells the creator to upload a square image, and the admin preview is 1:1.
- **Evidence:** `apps/api/src/media/cover.ts:7-8` (`COVER_SIZE = 1400`), `:20` ("DESIGN.md: covers are 1:1"), `:37` (`resize(1400, 1400, { fit: 'cover' })`); `apps/admin/src/i18n/mn.ts:270` ("Дөрвөлжин (1:1) зураг тохиромжтой"); `apps/admin/src/admin.css:503` (`aspect-ratio: 1 / 1`); test `admin-uploads.test.ts:295,309` asserts 1400×1400. Mobile expects 16:9: `apps/mobile/src/ui/EpisodeThumb.tsx:15,52`, `EpisodeCard.tsx:21`.
- **Reproduce:** Upload a 1280×720 picture → the stored WebP is 1400×1400 with the left and right cut off.
- **Fix:** Write a new ADR superseding ADR-0021 #5 (and the square-cover line of ADR-0011), then produce 16:9 variants (for example 1280×720 + 640×360). Keep the 4:3 list crop on the client. Fix the admin hint and preview, and update the tests.
- **Scope:** IN (ADR-0028, DESIGN) · **Confidence:** VERIFIED

#### B-04 · P1 · UNVERIFIED: no live proof that the pull zone refuses unsigned, expired or tampered links

- **What:** Our signer matches Bunny's reference code, but refusal depends on Token Authentication being switched ON in the pull zone. `bunny:smoke` has never been run. If token auth is off, every audio URL is public.
- **Evidence:** [[R-bunny-token-auth]] ("Not yet checked against a live zone"); "Run `bunny:smoke`" is still under Next in `docs/log/2026-10-08.md` and `2026-10-09.md`.
- **Reproduce:** `pnpm --filter @ongod/api bunny:smoke` from a network that reaches Bunny. Then request the file with no token and with a past `expires`: both must return 403.
- **Fix:** Run it on the dev zone now and on the owner's zone at the switch ([[BUNNY_SWITCH]] step 6). Log the result and mark the research note live-verified.
- **Scope:** IN (acceptance test "a link without access or token is refused") · **Confidence:** UNVERIFIED (needs a live zone)

#### B-05 · P2 · An audio asset can stay PROCESSING forever, which blocks both re-upload and Retry

- **What:**
  - When a `media.audio-upload` job's lock times out on its last attempt, stale-job recovery marks the Job FAILED but leaves the MediaAsset PROCESSING.
  - A new upload is refused while the asset is PROCESSING (409), and Retry accepts only FAILED, so the episode needs DB surgery.
  - The lock timeout (15 min) is shorter than the Bunny PUT timeout (30 min), so a slow upload can be claimed and run twice in parallel.
- **Evidence:** `jobs/worker.ts:45` (lock 15 min), `:70-77`; `lib/bunnyStorage.ts:86` (30 min); `media/tus.ts:57-58`; `admin/content.ts:343`.
- **Reproduce:** Kill the process during the last attempt of an audio upload and wait 15 min → asset stuck PROCESSING; a new upload gets 409.
- **Fix:** Make the lock timeout longer than the PUT timeout. When recovery fails an audio job, mark its asset FAILED with a reason (or let Retry accept an old PROCESSING asset).
- **Scope:** IN · **Confidence:** UNVERIFIED (reasoned from code, not run)

#### B-06 · P2 · A signed audio URL plays on any device or IP for up to 4 h (accepted risk)

- **What:** The brief expects "a link from a third device is refused". By design it is not ([[ADR-0020-bunny-signed-urls-hs256-no-ip|ADR-0020]] #2, ADR-0021). The device check only controls who can _get_ a URL. The URL itself is a bearer link to the whole file until min(now + 4 h, accessUntil).
- **Evidence:** `catalog/service.ts:266-270` (device check before signing), `:281-283` (expiry); signer oracle script.
- **Reproduce:** Copy the URL from `POST /v1/episodes/:id/play` into another browser → it plays (enforced by Bunny, not by us).
- **Fix:** If this is not acceptable, cut the TTL to 30–60 min. The mobile controller already re-signs when less than 60 s is left.
- **Scope:** IN (accepted in ADR-0004, ADR-0020, ADR-0021) · **Confidence:** signer VERIFIED; edge behaviour UNVERIFIED

#### B-07 · P2 · Portal and admin browser logins use the member's 2 device slots

- **What:** Every login, whatever its platform, goes through `registerDevice`. A member who pays in the portal on a laptop has one phone slot left. Every new admin browser takes a slot.
- **Evidence:** `auth/service.ts:249` (no platform exemption); `test/web-session.test.ts:182` (3rd device = DEVICE_LIMIT); [[open-questions]] #15.
- **Reproduce:** Log in on 2 phones, then in the portal → DEVICE_LIMIT.
- **Fix:** Decide #15, for example exempt `web`/`admin` from `MAX_DEVICES` or give them a separate small limit.
- **Scope:** IN (open decision) · **Confidence:** VERIFIED

#### B-08 · P2 · Category photos are not supported anywhere

- **What:** DESIGN: category cards show the category photo (`coverPath`), and admin has a category cover upload. There is no upload route or UI, nothing ever sets `Category.coverPath`, and the catalog category DTO has no cover URL. The Home "Сэдвээр сонсох" cards cannot show photos.
- **Evidence:** `apps/api/src/routes/admin-content.ts:70-99` (no category cover route); `coverPath` in `apps/api/src` is only episode code; `packages/shared/src/catalog.ts:15-21`.
- **Reproduce:** Try to give a category a photo: there is no UI or API for it.
- **Fix:** `POST /v1/admin/categories/:id/cover` reusing the cover job, plus a signed `coverUrl` on the category schema.
- **Scope:** IN (DESIGN "Artwork", "Admin screens") · **Confidence:** VERIFIED

#### B-09 · P3 · Re-uploading audio on a PUBLISHED episode deletes the old Bunny file at once

- **What:** Listeners holding a URL to the old file (valid up to 4 h) fail on their next range request, in the middle of the episode.
- **Evidence:** `media/jobs.ts:95-106`.
- **Reproduce:** Play an episode, re-upload its audio in admin, seek forward on the old URL.
- **Fix:** Queue the old-file delete with `runAt = now + PLAY_URL_TTL`.
- **Scope:** IN · **Confidence:** VERIFIED (code)

#### B-10 · P3 · Orphaned local files and crash windows in the upload pipeline

- **What:**
  - `onUploadFinish` moves the file and deletes the tus record before the DB commit; a crash in between leaves the asset UPLOADING forever and the file orphaned.
  - A new upload deletes FAILED/UPLOADING asset rows but not their files in `UPLOADS_DIR/audio`.
  - A job that crashes after commit never removes its local copy.
  - On a shared-hosting disk quota these files pile up.
- **Evidence:** `media/tus.ts:60-62,94-111`; `media/jobs.ts:95-119`.
- **Reproduce:** Kill the process between the rename and the transaction; or replace a FAILED upload twice and list `UPLOADS_DIR/audio`.
- **Fix:** A cron sweep that removes audio files with no live asset and marks stale UPLOADING assets FAILED.
- **Scope:** IN · **Confidence:** VERIFIED by reading

#### B-11 · P3 · The API lets an episode be scheduled with no audio or cover

- **What:** `schedule()` does not check `missing`. The cron then silently skips the episode, with no warning. The admin UI disables the button, so only direct API calls hit this.
- **Evidence:** `admin/content.ts:266-280`; `cron/tasks.ts:117-123`; `apps/admin/src/pages/EpisodeEdit.tsx:366`.
- **Reproduce:** `POST /v1/admin/episodes/:id/schedule` on a draft with no audio → 200; it is never published.
- **Fix:** Refuse with `NOT_READY_TO_PUBLISH`, like `publish`.
- **Scope:** IN · **Confidence:** VERIFIED

## C. Auth and accounts

Checked and OK:

- **Passwords:** argon2id (`auth/crypto.ts:9`). Minimum 8 characters enforced on the server for register, reset, change and complete-profile (`packages/shared/src/auth.ts:23`).
- **Access JWT:** pinned to HS256 (`crypto.ts:60-62`). `sid` is checked against the Session row on every request (`guard.ts:34-45`); lifetime 900 s.
- **Refresh tokens:** 32 random bytes stored as SHA-256 hashes, rotated with a precondition. Reuse or a deviceId mismatch revokes the whole family (`service.ts:385-401`).
- **Email codes:** CSPRNG, stored as HMAC, attempts counted atomically (5), 10-minute expiry, single use, 60 s resend (`service.ts:87-151`). Password reset revokes all sessions (`:460`).
- **Admin TOTP:** replay precondition; setup refused once enabled; role read from the DB on every request (`admin/totp.ts:26-62`).
- **Cron secret:** compared in constant time (`routes/cron.ts:11-15`).
- **Social flag off:** routes return 404 (`app.ts:133`).
- **Web cookie:** httpOnly, SameSite=Strict, `Path=/v1/auth`, plus an Origin check (`auth/web-session.ts:21-46`).
- **429 shape:** uses `{error:{code,message}}` (`errors.ts:54-65`, `app.test.ts:103-108`).
- **Admin routes:** **every admin route has a guard.**

#### C-01 · P1 · Per-IP limits will lock out real users behind one carrier IP on launch day

- **What:**
  - Refresh shares the auth limiter: 30 per IP per 15 min (`AUTH_RATE_LIMIT_IP_MAX`). Access tokens live 15 min, so every active app refreshes about every 15 min. More than about 30 active users behind one public IP (mobile carrier NAT, office, campus) start getting 429 on refresh.
  - On start-up the app then treats the 429 as "signed out" (H-04).
  - Login, register and the code routes share the same per-IP budget.
  - The global limit of 300 requests/min per IP also counts portal and admin static files, `/health`, the 15 s progress saves, play and tus chunks; about 75 listeners behind one IP use it up with progress saves alone.
  - `TRUST_PROXY` defaults to `false` with no production check. If it is forgotten behind the host proxy, every user shares the proxy IP and the whole site returns 429.
- **Evidence:** `apps/api/src/routes/auth.ts:72-73` (`// Per IP only` … `limiter.check(req, 'refresh', body.deviceId)`); `auth/rate-limit.ts:56-61`; `env.ts:37,39,65-67` (defaults 300/min, 30 per 900 s, `TRUST_PROXY` false); `app.ts:101-104` (no keyGenerator, no exemptions); mobile `src/api/client.ts:137-145`. Probe via Fastify inject (same IP, max=2): `200,200,429,429`.
- **Reproduce:** 31 refreshes (or logins) from one IP within 15 min → 31st = `429 RATE_LIMITED`.
- **Fix:** Drop the per-IP limit on refresh (the token is unguessable; keep per-device). Key the global limit by user id for authenticated routes and exempt static files and `/health`. Raise the per-IP auth ceilings and rely on per-identifier keys. Refuse to start in production without an explicit `TRUST_PROXY`.
- **Scope:** IN · **Confidence:** code VERIFIED. How many users Mongolian carriers put behind one IP is UNVERIFIED; if many, this is effectively P0 on launch day.

#### C-02 · P2 · `trustProxy: true` trusts the client-controlled X-Forwarded-For, so per-IP limits can be spoofed

- **What:** With `trustProxy: true`, `req.ip` is the left-most X-Forwarded-For entry. If the iTools proxy appends to that header, a client picks its own IP per request and the per-IP login/code limits never trigger.
- **Evidence:** `app.ts:83`; [[DEPLOY]] requires `TRUST_PROXY=true`. Probe: forged `X-Forwarded-For` → `req.ip` = forged value; 5 of 5 requests passed with max=2.
- **Reproduce:** Send each login with a new forged `X-Forwarded-For`.
- **Fix:** `trustProxy: 1` (hop count) or the proxy's IP/CIDR.
- **Scope:** IN · **Confidence:** library behaviour VERIFIED; iTools header handling UNVERIFIED

#### C-03 · P2 · The per-identifier login limit can be bypassed with accented variants

- **What:** The identifier is only trimmed and lowercased. Tables use `utf8mb4_unicode_ci` (accent-insensitive), so `bàt` finds user `bat` but counts under a different limiter key. Combined with C-02, password guessing is bounded only by argon2 cost.
- **Evidence:** `packages/shared/src/auth.ts:9,99`; `auth/service.ts:340-342`; `rate-limit.ts:59`; `prisma/migrations/20261008055104_init/migration.sql:21`.
- **Reproduce:** `POST /v1/auth/login` with `bat`, `bàt`, `bát`, … → 10 attempts per variant.
- **Fix:** Allow only `[a-z0-9._@+-]` in the login identifier, or count failures per resolved user id.
- **Scope:** IN · **Confidence:** code VERIFIED; DB comparison not run (documented MySQL behaviour)

#### C-04 · P2 · Anyone can lock a known user out of login and out of email codes

- **What:** The per-identifier counter counts every attempt, from any IP, before the password check. Eleven bad logins per 15 min for a known username (for example the store reviewer's demo account) block that user everywhere. Spamming forgot-password with a victim's email uses up the shared `code` scope, so the victim cannot verify or reset.

- **Reproduce:** 11 wrong logins for the demo user, then the right password → 429.
- **Fix:** Count only failures; key on (IP, identifier); keep a higher global per-identifier ceiling.
- **Scope:** IN · **Confidence:** VERIFIED (code)

#### C-05 · P2 · Registration deadlock is still unfixed

- **What:** `register` creates the user, then `issueCode` runs `updateMany` on an empty `(userId, purpose)` range (a gap lock) and then inserts. Two sign-ups at the same moment deadlock (MySQL 1213, Prisma P2034). Nothing retries, so the user gets a 500 and the owner an alert. Forgot-password and resend can collide the same way. Launch-day sign-ups are bursty.
- **Evidence:** `auth/service.ts:98-111` (inside the transaction at `:292-305`); no `P2034` handling outside the job worker; seen in `docs/log/2026-10-09.md`.
- **Reproduce:** Two simultaneous `POST /v1/auth/register` with different emails → one 500.
- **Fix:** Skip the `updateMany` for a brand-new user; retry transactions on P2034 up to 3 times; add a parallel-register test.
- **Scope:** IN · **Confidence:** unfixed VERIFIED; frequency UNVERIFIED

#### F-02 · P2 · One sequential worker: email codes wait behind Bunny uploads and slow SMTP

- **What:** The worker runs claimed jobs one after another. A 22–40 MB `media.audio-upload`, or an SMTP connection hanging on nodemailer's default 10-minute socket timeout, delays every verification and reset code. Those codes expire after 10 minutes.
- **Evidence:** `jobs/worker.ts:43` (batch 5), `:126-129` (`for (const job of jobs) await this.execute(job)`); `email/mailer.ts:11-16` (no timeouts).
- **Reproduce:** Upload 3 episodes, then register → the code email goes out after the uploads.
- **Fix:** A separate lane or priority for `email.*` (or run media jobs concurrently); set SMTP `connectionTimeout`/`socketTimeout`.
- **Scope:** IN · **Confidence:** code VERIFIED; real delays UNVERIFIED (host bandwidth)

#### F-03 · P2 · Session and EmailCode tables grow forever

- **What:** Every refresh inserts a new Session row, and nothing deletes expired or revoked sessions or used/expired codes. Family-revoke and revoke-all queries scan growing sets.
- **Evidence:** `auth/service.ts:186-196,404-410`; no purge task in `cron/tasks.ts:159-165`.

#### F-04 · P3 · Side effects can repeat after a crash (at-least-once delivery)
